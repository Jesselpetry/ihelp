# คู่มือการจัดการเวอร์ชันและการบันทึกประวัติ (Version Control & Changelog Guide)

คู่มือนี้กำหนดระเบียบและมาตรฐานการกำหนดเลขเวอร์ชัน (Versioning Scheme), การบันทึกประวัติการเปลี่ยนแปลงใน `CHANGELOG.md`, และการผูกข้อมูลเข้ากับหน้าเว็บ `/version` (`lib/docs/changelog.ts`) สำหรับทีมงานและผู้ร่วมพัฒนา \<i\>Help

---

## 1. ปรัชญาและโครงสร้างเลขเวอร์ชัน (Versioning Principles)

\<i\>Help ยึดหลักการของ **[Semantic Versioning 2.0.0](https://semver.org/lang/th/)** (`MAJOR.MINOR.PATCH`) ควบคู่กับการจัดกลุ่มตามวันและไมล์สโตน (Daily / Milestone Grouping):

```
v MAJOR . MINOR . PATCH
   │        │       └── แก้ไขบั๊ก, ปรับปรุงเล็กน้อย, ปรับคำ, หรือรอบอัปเดตประจำวันถัดไป
   │        └────────── ฟีเจอร์ใหม่, สรุปเนื้อหาวิชาใหม่, เครื่องมือใหม่ (ไม่ทำลายระบบเดิม)
   └─────────────────── การเปลี่ยนสถาปัตยกรรมใหญ่ หรือ Breaking Changes
```

### 1.1 กฎการจัดกลุ่มงานรายวันและข้ามวัน (Daily & Overnight Workflow)
เพื่อให้ผู้ใช้งานและผู้ร่วมพัฒนารู้แน่ชัดว่าเว็บที่กำลังรันอยู่คือเวอร์ชันอะไร:

1. **งานที่เสร็จสิ้นในวันเดียวกัน (Same-Day Batch):**
   - การแก้ไขไฟล์และฟีเจอร์หลายรายการที่เสร็จสิ้นภายในวันเดียวกัน ให้รวม (bundle) เป็นเวอร์ชันเดียวกัน โดยลงวันที่ของวันนั้น (เช่น `v0.9.0` — `7 พฤศจิกายน 2569`)
2. **งานที่ทำต่อเนื่องข้ามวัน (Overnight & Next-Day Updates):**
   - หากมีการแก้งานต่อเนื่องข้ามคืนและปล่อยในวันถัดไป ให้ขยับเลข Patch ขึ้นหนึ่งลำดับ (เช่น `v0.9.1` — `8 พฤศจิกายน 2569`) เพื่อให้เห็นความแตกต่างของเวอร์ชันอย่างชัดเจน
3. **งานที่กำลังอยู่ระหว่างการพัฒนา (Work in Progress):**
   - หลีกเลี่ยงการใช้คำว่า "Unreleased" ลอยๆ โดยไม่มีเลขกำกับ เพราะจะทำให้ผู้ใช้สับสนว่าระบบเป็นเวอร์ชันอะไร
   - ให้ระบุเลขเวอร์ชันเป้าหมายพร้อมสถานะ เช่น `v0.9.1 (กำลังพัฒนา / In Development)` หรือระบุเลขไมล์สโตนปัจจุบันให้ชัดเจน

## 2. มาตรฐานการเขียน `CHANGELOG.md`

ไฟล์ `CHANGELOG.md` ที่รากของ repository อ้างอิงตาม [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/) โดยปรับให้เป็นมิตรกับนักศึกษาไทย:

### 2.1 โครงสร้างหัวข้อแต่ละเวอร์ชัน
```markdown
## [0.9.0] - 7 พฤศจิกายน 2569

**ผู้ร่วมพัฒนา:** Chatan Petry ([@Jesselpetry](https://github.com/Jesselpetry), IG: [@chatann_](https://instagram.com/chatann_)), PhuPunnavit ([@PhuPunnavit](https://github.com/PhuPunnavit), IG: [@priiu_i](https://instagram.com/priiu_i))

### เพิ่ม
- **ชื่อฟีเจอร์ตัวหนา** — คำอธิบายผลลัพธ์ที่ผู้ใช้หรือนักศึกษาจะได้รับ

### ปรับปรุง
- **ส่วนที่ปรับปรุง** — คำอธิบายความเปลี่ยนแปลงด้าน UX, ดีไซน์ หรือประสิทธิภาพ

### แก้ไข
- **บั๊กที่ได้รับการแก้ไข** — คำอธิบายบั๊กและผลหลังแก้ไข

### ความปลอดภัย
- **การยกระดับความปลอดภัย** — คำอธิบายโดยสรุป (ไม่เปิดเผยช่องโหว่ที่ล่อแหลม)
```

### 2.2 ข้อกำหนดภาษาและข้อห้าม
- **หัวข้อย่อย:** ใช้ภาษาไทย 4 หมวดเสมอ: `### เพิ่ม` · `### ปรับปรุง` · `### แก้ไข` · `### ความปลอดภัย`
- **วันที่:** ระบุเป็นวันที่ภาษาไทยพร้อมปี พ.ศ. (เช่น `7 พฤศจิกายน 2569`)
- **ความปลอดภัย & สิทธิ์:** ห้ามระบุรายละเอียดข้อสอบเก่าที่จำกัดสิทธิ์ หรือขั้นตอนการข้ามระบบความปลอดภัย

## 3. การผูกข้อมูลเข้ากับหน้าเว็บ `/version` (`lib/docs/changelog.ts`)

หน้า `/version` ของเว็บไซต์ใช้ข้อมูลแบบ Static Type-safe สองภาษา (`th` / `en`) จาก `lib/docs/changelog.ts`:

```ts
export interface VersionEntry {
  version: string;          // e.g. "0.9.0"
  date: string | null;      // ISO string "2026-11-07" หรือ null สำหรับงานที่กำลังพัฒนา
  commit?: string;          // Short Git commit hash (7 ตัวอักษร เช่น "7e91359")
  contributors: Contributor[];
  changes: ChangeEntry[];
}
```

### 3.1 การซิงค์ระหว่าง `CHANGELOG.md` และ `lib/docs/changelog.ts`
1. เมื่อทำการตัดรอบเวอร์ชัน (Release) ให้ใส่ข้อมูลทั้งใน `CHANGELOG.md` (Markdown ภาษาไทย) และ `lib/docs/changelog.ts` (TypeScript พร้อมคำแปลภาษาอังกฤษ)
2. สำหรับผู้ร่วมพัฒนาทั่วไปที่ส่ง PR ให้เพิ่มรายการใน `CHANGELOG.md` ใต้เวอร์ชันปัจจุบันหรือไมล์สโตนที่กำลังพัฒนา ส่วน `lib/docs/changelog.ts` ผู้ดูแลหลัก (Maintainer) จะเป็นผู้จัดทำคำแปลสองภาษาและตรวจความเรียบร้อยก่อน Merge

## 4. Git Branching & Release Workflow

```
[feature/xxx] ──── PR ────► [staging] (Integration Branch) ──── Promote ────► [main] (Production)
                               │                                                 │
                        ทดสอบฟีเจอร์รวม                                   ปล่อยขึ้นระบบจริง
                     (เช่น Grade Calculator)                             (เฉพาะฟีเจอร์พร้อมใช้)
```

1. **`staging` เป็นกิ่งหลักในการพัฒนาร่วม:**
   - ทุก Pull Request ต้องแตกกิ่งและเปิด PR เข้าสู่ `staging` เสมอ
   - ฟีเจอร์ที่อยู่ในช่วงทดลอง (เช่น `/grade-calculator`) จะถูกทดสอบบน `staging` จนกว่าจะพร้อมปล่อยจริง
2. **`main` เป็นกิ่งสำหรับ Production Releases:**
   - รวมเฉพาะโค้ดที่ได้รับการทดสอบและยืนยันแล้ว
   - การปล่อยเวอร์ชันใหม่จะสร้าง Git Tag เช่น `git tag v0.9.0`
3. **Conventional Commits:**
   - ใช้รูปแบบ `type(scope): message` เช่น:
     - `feat(chat): add streaming responses`
     - `fix(modal): remove overlapping online badge`
     - `docs(version): add version control guide`
